# PART I — APPROVED ARCHITECTURE

## 3. Execution Model

Use a controlled AST interpreter for VisUAL execution.

The interpreter must execute only the explicitly supported Python subset. It must not use unrestricted `exec()` or `eval()` to execute user programs.

Keep normal Python execution separate from visualization execution.

The existing Run File action and Ctrl+R shortcut must retain their original behavior.

The preferred architecture uses a dedicated worker process for controlled execution, with structured messages exchanged between the worker and the UI.

The worker and trace system must support:

- Cancellation.
- Execution time limits.
- Maximum executed-step limits.
- Maximum trace-size limits.
- Clear syntax and runtime diagnostics.
- Deterministic trace generation.
- Cleanup after successful, failed, or cancelled runs.
- Protection against stale results from earlier executions overwriting a newer trace.

Do not describe this design as a universal security sandbox.

## 4. Module Responsibilities

Reuse existing modules where possible. Avoid duplicate or competing execution paths.

Expected responsibilities:

These names are architectural guidance. If equivalent modules already exist, extend them instead of creating redundant implementations.

# PART II — INTENT-BASED DETECTION

## 5. Purpose of Detection

VisUAL must determine whether the user is likely trying to visualize a linked-list program.

The presence of:

```python
from dsa import LinkedList
```

is a positive intent signal, not proof that the program uses a linked list.

It must not trigger visualization automatically by itself.

For example:

```python
from dsa import LinkedList

print("Hello World")
```

must not be classified as a strong linked-list candidate.

The import is unused, and the program has no meaningful linked-list structure or operations.

Conversely, conventional linked-list code without the import must still be eligible for detection.

## 6. Detection Signals

Analyze these signals using the Python AST and symbol-resolution information.

### Signal A: DSA import

Recognize supported import forms, including:

```python
from dsa import LinkedList
```

Treat the import as weak positive evidence.

Account for unused imports, aliases, reassignment, and name shadowing.

### Signal B: Conventional class definitions

Recognize conventional user-defined `Node` and `LinkedList` classes.

Inspect relevant definitions for evidence such as:

- A node data/value attribute.
- A node `next` reference.
- A linked-list `head` reference.
- A constructor that initializes the appropriate fields.
- Methods that traverse, connect, or modify nodes.

Do not require every possible linked-list method to exist before recognizing partial intent.

### Signal C: Actual linked-list usage

Look for meaningful operations, including:

- Creating a linked-list instance.
- Creating node instances.
- Assigning a node to `head`.
- Connecting nodes through `next`.
- Traversing references.
- Calling methods that insert, delete, or update nodes.
- Reading or changing node data.

### Signal D: Source-level and execution-path evidence

Distinguish definitions from executable usage.

Do not treat comments, strings, unrelated variable names, or an unused import as proof of linked-list behavior.

Handle class shadowing and name binding explicitly.

## 7. Detection Outcomes

Implement three explicit outcomes.

### Outcome 1: No linked-list intent

Examples:

- Hello World.
- An unused `dsa` import.
- A normal program containing no meaningful linked-list structure.
- Comments or strings that merely mention `Node`, `head`, or `next`.

When the user explicitly clicks Run VisUAL, show a clear dialog offering:

- Run Normal.
- Cancel.

Cancel must execute nothing.

### Outcome 2: Possible linked-list intent

Examples:

- A Node class exists, but no linked-list usage is found.
- A LinkedList class exists, but its structure is ambiguous.
- Partial linked-list code exists without sufficient evidence of a supported implementation.

Show a confirmation dialog explaining what was detected and what remains uncertain.

Offer normal execution or cancellation. Do not invent a visualization.

### Outcome 3: Strong linked-list intent

Examples:

- Conventional Node and LinkedList classes exist.
- The program creates a list instance.
- Supported operations create, connect, traverse, or modify nodes.

Continue into syntax validation and controlled execution.

Strong intent does not mean the program is automatically supported.

If unsupported syntax is present, display an actionable diagnostic rather than producing an inaccurate trace.

## 8. Detection and Validation Must Remain Separate

The following stages must remain distinct:

1. Intent detection.
2. Supported-syntax validation.
3. Controlled interpretation.
4. Trace recording.
5. Visualization.

Do not use a detection score as a substitute for validation.

A numeric score may be exposed for debugging, but deterministic evidence and explicit outcome levels must drive the UI.

The result should include fields equivalent to:

- `intent_level`
- `score`, if used
- `signals`
- `evidence`
- `diagnostics`
- `is_supported`

Provide source locations where possible.

# PART III — SUPPORTED PYTHON CONTRACT

## 9. Initial Supported Subset

Support conventional singly linked-list implementations with:

- User-defined `Node` and `LinkedList` classes.
- Supported `__init__` methods.
- Instance attributes such as `self.data`, `self.next`, and `self.head`.
- Local variables and supported assignments.
- `None`, integers, strings, and booleans.
- Supported attribute access.
- `if` and `else`.
- `while` loops.
- Comparisons.
- `return`.
- `break`.
- Defined early-return behavior.
- Supported user-defined method calls.
- `print()` with supported values.
- Traversal, insertion, deletion, and updating.

The exact expression grammar, operators, call rules, and assignment rules must be documented and tested.

## 10. Unsupported Features

Reject unsupported constructs with clear diagnostics, including:

- Imports and dynamic external dependencies in the controlled execution path, except for any explicitly implemented and tested compatibility behavior.
- Arbitrary file or network access.
- `eval()` and `exec()`.
- Reflection and dynamic code execution.
- Async functions and generators.
- Unsupported inheritance and descriptors.
- Recursion unless explicitly approved and implemented.
- Unsupported built-ins or object behaviors.
- Linked-list patterns outside the documented contract.

If the source contains `from dsa import LinkedList` and also defines its own `LinkedList`, resolve which definition is actually used. Never assume that the imported name and user-defined class are the same object.

# PART IV — TRACE AND OBJECT IDENTITY

## 11. Stable Object IDs

Fix any object-ID instability in the current implementation.

Object identity must be independent of:

- The current trace-step index.
- The number of times an object is referenced.
- The variable name holding the reference.
- The number of snapshots recorded.
- UI rendering or formatting.

Assign an ID once when an object is created and preserve that identity throughout its lifetime in the trace.

All references to the same object must resolve to the same ID.

For example, if:

```python
ll = LinkedList()
```

creates LinkedList object #1, then `ll` and `self` inside methods executing on that same object must both refer to object #1.

However, `self` inside `Node.__init__` refers to the newly created Node, not the LinkedList. Its ID must therefore match that Node's ID.

A variable such as `current` may legitimately change IDs when it is reassigned to another node.

Do not incorrectly force every variable named `self` to have the same ID globally.

## 12. Object Registry

Use a persistent object identity registry or an equivalent identity mechanism.

Requirements:

- IDs are assigned once.
- References reuse existing IDs.
- Snapshot creation does not create new identities.
- Object deletion does not retroactively alter earlier snapshots.
- Different objects with identical data values retain different IDs.
- Variables that alias the same object display the same ID.
- IDs remain consistent when navigating backward and forward.

Object IDs must reflect actual object identity, not a newly computed label for every step.

## 13. Trace Snapshot Contract

Each snapshot must be self-contained and immutable.

Include fields equivalent to:

- `step_index`
- `source`
- `event_type`
- `nodes`
- `next_refs`
- `head_ref`
- `variables`
- `explanation`
- `status`

Record sufficient before/after information to explain structural changes.

Supported event categories should include:

- Class definition.
- Method entry and return.
- Object creation.
- Variable assignment.
- Condition evaluation.
- Loop iteration.
- Node traversal.
- Head assignment.
- Link creation or replacement.
- Node-value update.
- Deletion-related link change.
- Output.
- Completion.
- Failure.

Do not generate a pointer-change event unless the corresponding reference actually changed.

Previous and Next must navigate recorded snapshots without re-executing the program.

# PART V — VISUAL DESIGN AND UX

VisUAL must not look like an empty canvas with a linked-list label.

The interface should teach four concepts:

1. The class definition.
2. The objects created from that definition.
3. The references and connections between those objects.
4. The operation that changed the program state.

Use a clean, restrained dark-theme design consistent with the existing Lau-PyDE interface.

Prioritize readability, useful space allocation, consistent alignment, and clear visual hierarchy over decorative effects.

## 15. Approved Workspace Layout

Use the existing nested horizontal splitter integration.

Preserve the existing IDE structure:

- Explorer.
- Source editor.
- Output panel.
- Terminal panel.

Add the VisUAL workspace alongside the editor/output area without destroying or replacing existing components.

The VisUAL workspace should contain:

1. Class Blueprint.
2. Linked-list visualization canvas.
3. Previous/Next controls and step indicator.
4. Variables and References.
5. Step Explanation.
6. Program output, separate from VisUAL explanations.

The Class Blueprint remains visible during execution but becomes compact when the live visualization needs more space.

The linked-list canvas receives the greatest share of available space.

Variables and explanations should be readable without forcing excessive scrolling.

Allow users to resize, hide, and reopen the VisUAL panel.

Restore Layout must return the IDE to its standard layout.

Closing VisUAL must not destroy the editor or alter source contents.

## 16. Class Blueprint

Implement a persistent Class Blueprint panel based on the analyzer's metadata.

It must display:

### Node blueprint

Show recognized attributes such as:

- `data`
- `next`

Show the constructor and other relevant methods when useful.

### LinkedList blueprint

Show recognized attributes such as:

- `head`

Show actual methods discovered in the user's source, such as:

- `insert_end()`
- `traverse()`
- `delete()`
- `update()`

Do not hardcode the method list to a specific example.

Only show methods and attributes that actually exist or are reliably inferred from the source.

### Blueprint behavior

- Highlight the currently executing class or method.
- Clicking a method navigates to its definition.
- Distinguish class definitions from instantiated objects.
- Keep the blueprint compact but available throughout execution.
- Make it collapsible if space is limited.

A blueprint is conceptual metadata. It must not be represented as a live Node object.

## 17. Adaptive Visualization States

Implement three presentation modes driven by the trace.

### State A: Blueprint

Before any relevant object exists:

- Show the Class Blueprint prominently.
- Explain that the classes have been defined but no linked-list instance or nodes exist yet.
- Show an appropriate empty-state illustration or compact structural summary.
- Avoid a blank canvas.

Example:

"Class definitions loaded. Waiting for the first LinkedList instance."

Only show that message when the recorded state supports it.

If a LinkedList object already exists but has no nodes, explain that its head is `None`.

### State B: Initialization

As objects are created:

- Show the LinkedList object.
- Show newly created Node objects.
- Show their actual initialized fields.
- Show assignments to `head` and `next`.
- Highlight the object or reference involved in the current step.

Do not display a Node as existing before its constructor actually creates it.

### State C: Active linked list

When nodes exist:

- Make the live linked-list diagram the main focus.
- Keep the Class Blueprint compact and visible.
- Show the head pointer.
- Show node data and next references.
- Highlight traversal and pointer changes.
- Show the corresponding variables and explanation.

These are presentation modes, not separate interpreters or execution engines.

## 18. Empty-State Accuracy

Never use fabricated values to make the canvas appear populated.

For the conventional Node definition:

```python
class Node:
    def __init__(self, data):
        self.data = data
        self.next = None
```

The blueprint may display:

```text
Node
  data: value
  next: Node | None
```

The live instance must display the actual data passed to its constructor.

Do not display `data = []` for a Node whose data is uninitialized or unknown. An empty list and a missing or unknown value are different concepts.

Use `None` only when the actual recorded value is `None`.

The empty state must explain the current program state without pretending that objects or links exist.

## 19. Linked-List Renderer

Render each actual node as a clear, readable box.

Each Node box should show:

- Stable object ID.
- Actual data value.
- Next reference or null marker.

Show a distinct head pointer.

Draw arrows that correspond to actual next references.

Support:

- Empty lists.
- Single-node lists.
- Multiple nodes.
- Duplicate node values.
- Long lists.
- Responsive wrapping or scrolling.
- Selected-node highlighting.
- Newly created and deleted nodes.
- Null references.
- Correct layout after stepping backward.

When a node is deleted, earlier snapshots must still show it. Later snapshots must reflect its removal from the live structure.

Do not treat two nodes with the same data value as the same object.

## 20. Transition Highlighting

Highlight the actual change associated with the selected trace event.

Examples:

- Object creation: emphasize the new object.
- `self.head = new_node`: highlight the head assignment.
- `current.next = new_node`: highlight the changed pointer and new connection.
- `current.data = new_data`: highlight the updated data field.
- Traversal: highlight the current node without inventing a structural mutation.
- Deletion: highlight the link change and resulting live structure.

Use restrained, consistent color semantics:

- Neutral: unchanged objects and references.
- Blue: current execution focus.
- Green: newly created objects or successful connections.
- Amber: a value or reference being changed.
- Red: removed connections or failure states, with appropriate context.

Do not rely on color alone to convey meaning.

Restore the correct highlights when navigating backward and forward.

## 21. Variables and References

Implement a presentation-only formatter for variable values.

Keep the interpreter's internal object representation unchanged.

For example, internal metadata may look like:

```python
{"ref": 4, "class": "Node"}
```

Display it as:

```text
4
```

Expected display:

```text
ll = 1
self = 1
data = 133
new_node = 4
current = 3
```

Use the original variable names from the program by default.

Do not silently rename `ll` to `linked_list`.

If friendly aliases are added later, make them explicit display metadata rather than modifying the program or trace.

Display rules:

- LinkedList references: object ID.
- Node references: object ID.
- `self`: ID of the actual current object.
- Integers, strings, and booleans: actual values.
- `None`: `None`.
- Unsupported or unknown values: clear, non-misleading fallback.

Selecting a reference should highlight the corresponding object.

If two variables reference the same object, their displayed IDs must match.

The display formatter must never mutate snapshots or assign new object IDs.

## 22. Step Explanation

Every relevant step should have a short, understandable explanation.

Where the event provides sufficient evidence, explain:

- What statement executed.
- What value or reference changed.
- Why the change matters to the linked list.
- The corresponding source line.

Example:

Action:
`current.next = new_node`

What happened:
"Node #2 now points to Node #4."

Why it matters:
"This connects the new node to the end of the linked list."

Source:
"Line 23."

Generate explanations from actual interpreter events and trace state. Do not claim insertion, deletion, or success if the corresponding operation did not occur.

## 23. Navigation and Interaction

Provide:

- Previous.
- Next.
- Current step / total steps.
- Jump to start.
- Jump to end.
- Current execution status.
- Node selection.
- Variable selection.
- Source navigation.
- Panel hide/show.

Disable Previous at the first step and Next at the last step.

Selecting a node or variable must not alter program execution.

Clicking a source location should navigate to the appropriate editor line without modifying source contents.

Use the existing editor highlighting facilities wherever possible.
