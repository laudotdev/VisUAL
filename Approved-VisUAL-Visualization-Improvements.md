# VisUAL Visualization Improvements

## Purpose

VisUAL is an educational program-visualization project intended to make Python data structures and algorithms easier to understand. Its existing experience records supported program execution and lets a learner inspect the resulting states step by step.

This document is the approved planning and implementation reference for improving that experience. It describes the problems identified in the current system, the educational reasons they matter, the approved design decisions, and the criteria that will be used to evaluate a later implementation.

The goal is not merely to display the final data structure. The goal is to help a learner understand the sequence of events that produced the selected state: what executed, what changed, why it changed, and what each relevant variable means.

## Background and Current Behavior

The repository contains a controlled AST-based execution path in `visual/interpreter.py`. It validates and interprets a supported subset of Python, records immutable execution snapshots through `visual/trace.py`, and returns generated output separately from those snapshots.

The current visualization pipeline includes:

- `visual/interpreter.py`, which executes supported programs and records source locations, event types, node data, references, variables, explanations, output history, and traversal references.
- `visual/trace.py`, which detaches snapshots from later runtime mutation and performs basic consistency checks.
- `visual/linked_list_view.py`, which renders the reachable linked-list chain from `head`, its `next` arrows, the head marker, node values, and the green traversal highlight.
- `visual/visualizer_panel.py`, which provides the Step Explanation panel, the Variable Explanation panel, Program Output, and Previous/Next navigation.
- `visual/presentation.py`, which formats serialized values for display.
- `visual/analyzer.py`, which determines whether source code falls within the supported execution contract.
- `tests/`, which contains tests for analysis, interpreter behavior, linked-list presentation, and value formatting.

The current system already has important behavior that must be preserved: recorded states, stable object references within a trace, linked-list node rendering, source-step synchronization, navigation, output history, and traversal highlighting. The improvements in this document extend that architecture; they do not authorize replacing it with a second visualization engine.

The current repository also includes `ground_linked_list/LinkedList_Stack_Queue-Module.pdf`, which is the supplied educational reference for the concepts covered by this work.

### Distinct responsibilities

The implementation and documentation must keep these related concepts separate:

| Responsibility | Meaning |
| --- | --- |
| Program execution | What the supported execution environment actually executes. |
| Runtime state | The current objects, variables, attributes, and references in memory. |
| Visualization | The visual representation selected for the current event and runtime state. |
| Step Explanation | Human-readable text describing what happened and why it matters. |
| Variable Explanation | Contextual information about relevant variables, attributes, values, and object relationships. |
| Program Output | Text actually generated by executed output statements. |

Runtime state must not be treated as output. A node can exist in memory without ever being printed.

## Identified Problems

### A. Class definitions receive the wrong visual emphasis

When execution reaches a definition such as:

```python
class Node:
    def __init__(self, data):
        self.data = data
        self.next = None
```

VisUAL may show an empty linked list with a message that no nodes exist. That can be technically true: defining a class does not create a `Node` instance. However, an empty-list diagram does not explain the event currently being executed. A beginner needs to see that `Node` is a blueprint and that its attributes describe future objects.

The requirement is event-aware visualization selection. The problem is not simply whether the empty-list representation is valid; it is whether it is the most informative representation for the selected event.

### B. Variable Explanation can be confusing

An entry such as:

```text
ll = LinkedList object (reference 1)
Refers to the linked list object ll.

self = LinkedList object (reference 1)
Refers to the linked list object self.
```

can make `ll` and `self` sound like separate objects, even though they may refer to the same object while an instance method executes. Numeric reference identifiers are useful internally, but they should not be the primary explanation shown to a beginner.

The identified presentation and educational problems include:

- excessive reliance on numeric reference identifiers;
- repeated or redundant explanations;
- unnecessarily long entries;
- unclear separation between a name, its current value or target, and its explanation;
- poor readability when many variables are displayed; and
- insufficient emphasis on each variable's role in the current operation.

These are requirements for clearer presentation. A specific layout defect must not be claimed as confirmed unless it has been verified in the implementation.

### C. Step Explanation may expose encoding or rendering artifacts

An execution message such as:

```text
output: Printed '14' to Program Output.
```

must appear as readable explanatory text. If HTML entities or other encoded text appear in the user-facing message, the encoding and rendering path must be investigated and corrected at the appropriate layer. The solution must not be a blind global string replacement that could corrupt legitimate content.

### D. Runtime state and Program Output are different concepts

A node containing `14` may exist in memory even though the program has not printed `14`. The linked-list view and Variable Explanation describe runtime state; Program Output must contain only text produced by executed output statements.

This distinction must also survive navigation. Selecting an earlier recorded state must not show output that only occurred in a later state.

### E. Intermediate states are not informative enough

An operation may create an object, assign a reference, and update `head` in separate execution steps. Showing only the final linked list hides the reasoning that a learner needs in order to understand the operation.

When the trace records meaningful intermediate states, VisUAL must make the actual order visible and explain the affected reference or object. It must not synthesize states that the execution did not produce.

## Approved Design Approach

The following decisions are approved for implementation. They are requirements for the next development phase, not claims that every behavior is already complete.

### Event-aware visualization

Select the most appropriate representation from the current execution event and runtime state. An empty linked list must not be used as a generic default whenever no reachable nodes exist.

| Current event or state | Appropriate representation |
| --- | --- |
| `Node` class definition | Node class blueprint |
| `LinkedList` class definition | LinkedList class blueprint |
| Linked-list object creation | The actual LinkedList object and its current state |
| Node creation | The actual Node object and its attributes |
| Reference assignment | The affected object and reference relationship |
| Linked-list operation | The current linked-list structure |
| Traversal | The linked list with the currently traversed node highlighted |
| Executed `print` statement | Updated Program Output alongside the relevant runtime view |

These are conceptual mappings, not instructions to create an independent visualization engine for every event. The existing trace and visualization pipeline should be extended wherever practical.

### Class blueprint versus actual object

A class blueprint describes a class, not an instance. A `Node` blueprint may explain that:

- `data` stores the node's value; and
- `next` holds a reference to the next node.

Defining `Node` must not create a runtime node. When an expression such as `Node(12)` executes, the visualization must show the actual object and its actual attributes, for example `data: 12` and `next: None`. Fictional objects, values, or references must never be added merely to make a diagram appear complete.

### Variable Explanation

The existing Variables and References presentation is approved to become a readable Variable Explanation panel. Each displayed entry must distinguish:

1. the variable or attribute name;
2. its current value or referenced object; and
3. a concise explanation of its role.

For example, during traversal:

```text
current
Current state: Node containing 14.
Explanation: Refers to the node currently being visited during traversal.

current.data
Current value: 14.
Explanation: The value stored in the current node.

current.next
Current value: None.
Explanation: The current node does not reference another node through next.
```

The actual entries must be derived from the selected snapshot. The panel should show variables relevant to the current event, explain relationships clearly, avoid redundant prose, keep numeric identities secondary, and remain technically accurate and readable.

### Method calls and `self`

A method-call explanation must connect the call expression, the object used to invoke it, and the actual arguments. For example:

```text
Method call: ll.insert_beginning(13)

self  ─────► LinkedList object: ll
data  ─────► 13
```

The explanation must make clear that `ll` is the variable used to invoke the method, `self` refers to that same linked-list object while the instance method executes, and `data` receives the argument `13`. `self` must not be described as a separate object merely because it has a different variable name.

### Step Explanation

Step Explanation should describe the current event in clear technical English. It should identify what happened, which object, variable, value, or reference was affected, and why the change matters when that context is useful.

Prefer:

> The linked list's head reference now points to the new node containing 13. The new node becomes the first node in the list.

Avoid exposing a raw internal event name as the only explanation. The text must describe the event that actually executed and must not claim a future state prematurely.

### Program Output

Program Output must contain actual output, not a description of the output event and not values inferred from runtime state.

Before an output statement executes:

```text
(no output yet)
```

After:

```python
print(current.data)
```

prints `14`, the panel should contain:

```text
14
```

If a later statement prints `20`, it should contain:

```text
14
20
```

The output must remain consistent with the selected recorded snapshot during Previous and Next navigation. Empty output must remain distinguishable from output containing `0`, `False`, or an empty string.

### Traversal highlighting

The existing green highlight for the node referenced by the traversal variable is approved for preservation and improvement. Traversal must:

- highlight the correct node;
- move the highlight as the traversal reference advances;
- explain the traversal variable's role;
- keep `head` distinct from the temporary traversal reference;
- avoid changing `head` incorrectly; and
- add Program Output only when the corresponding print statement executes.

This is an existing behavior to preserve, not a feature to replace.

### Meaningful intermediate states

For a method such as:

```python
def insert_beginning(self, data):
    new_value = Node(data)
    new_value.next = self.head
    self.head = new_value
    print(new_value.data)
```

the trace should distinguish, when those states are supported by the actual execution:

1. creation of the new node;
2. assignment of the new node's `next` reference;
3. assignment of the linked list's `head`; and
4. execution of the print statement.

The exact states must come from the recorded execution. The implementation must not fabricate events or assume that every operation follows this sequence.

## Educational Reference

`ground_linked_list/LinkedList_Stack_Queue-Module.pdf` is the primary educational reference for covered concepts. Its terminology and explanations should be used where relevant, including:

- classes and objects;
- nodes and references;
- `head` and the empty-list state;
- traversal;
- insertion, deletion, and searching;
- stack operations and LIFO behavior;
- queue operations and FIFO behavior;
- `front` and `rear`; and
- common beginner mistakes.

The module provides educational context, while the supported program execution determines the actual state. Additional technical explanations must remain accurate and must not be falsely attributed to the module. Mention of stack and queue concepts does not authorize adding new unsupported data-structure features.

## Architecture and Implementation Constraints

Future implementation work must:

- extend the existing VisUAL implementation rather than rebuild it from scratch;
- inspect the trace-state schema and visualization pipeline before changing them;
- preserve node layout, data values, `next` references, arrows, the head indicator, navigation, and traversal highlighting;
- maintain one authoritative execution state rather than creating duplicate sources of truth;
- derive explanations from actual events, state, variables, and references rather than hardcoding a supplied test program;
- avoid hardcoded node IDs, variable names, or data values;
- never invent runtime objects or events;
- preserve existing supported execution behavior;
- avoid unrelated features and unnecessary architectural changes;
- fix encoding and rendering problems at the appropriate layer; and
- use concise, meaningful comments instead of decorative comment banners.

Preferred comment style is short and explanatory, for example:

```python
# Explain the current node reference without changing the linked-list head.
```

Avoid decorative comments such as:

```python
# ====== Visualization ======
```

These are coding conventions for the implementation phase. This documentation task does not authorize code changes.

## Testing Strategy

The eventual implementation must be evaluated through behavior-focused tests and the existing test suite. Tests should inspect recorded states and user-facing representations, not merely the existence of labels.

The test strategy should cover:

- class definitions without accidental runtime instances;
- actual node creation and attributes;
- linked-list object creation and empty-list state;
- method calls, `self`, and argument mapping;
- context-sensitive Variable Explanation entries;
- multiple names referring to one object;
- readable Step Explanation text and encoding behavior;
- state without output versus actual printed output;
- output restoration while navigating recorded states;
- node creation, reference assignment, and head-update ordering;
- correct traversal highlighting and unchanged `head`; and
- preservation of existing analyzer, interpreter, trace, visualization, and presentation behavior.

Tests must be run against the implementation that is actually produced. This README does not claim that the approved improvements have been implemented or that these future tests have passed.

## Acceptance Criteria

The implementation will be considered acceptable only when evaluation demonstrates that:

1. A class definition is represented by an appropriate class blueprint.
2. Class definitions do not falsely create runtime instances.
3. Actual object creation displays the correct attributes.
4. Empty linked lists are represented appropriately when runtime state warrants it.
5. Method calls explain `self` and argument relationships correctly.
6. Variable Explanation is readable and context-sensitive.
7. Multiple variables referencing one object are explained accurately.
8. Step Explanation uses understandable text instead of exposing raw internal events as the sole explanation.
9. Raw HTML entities do not appear in plain-text explanatory messages.
10. Program Output contains only output actually generated by the program.
11. Previous and Next navigation restore consistent runtime state and output.
12. Intermediate reference changes appear in actual execution order when recorded.
13. Traversal highlighting remains correct.
14. Traversal does not incorrectly modify `head`.
15. Existing visualization and execution tests continue to pass.
16. New tests verify the improved behavior.
17. No unrelated features or unnecessary architectural rewrites are introduced.

These criteria are an evaluation checklist for the future implementation. They are not a claim that the current repository already satisfies every item.

## Scope and Non-Goals

This effort concerns the educational interpretation and presentation of the existing supported execution experience. It does not authorize:

- a rewrite of the interpreter or visualization engine;
- support for arbitrary Python syntax;
- new stack, queue, or other DSA operations solely because they are mentioned in the reference module;
- fictional runtime objects, predicted output, or synthesized trace states;
- unrelated UI redesigns or refactoring; or
- treating this README as evidence that implementation or testing is complete.

The supported-language contract remains important: a trustworthy limitation is better than a plausible but inaccurate diagram.

## Implementation Notes and Future Considerations

The next implementation phase should begin by comparing each approved behavior with the actual snapshot schema and rendering path. Decisions should be made against the selected snapshot so that source highlighting, the structure view, Variable Explanation, Step Explanation, and Program Output remain synchronized.

Optional future improvements may include broader object visualization or support for additional data structures, but they are outside this approved change unless separately specified and tested.

The governing principle is:

> VisUAL must visualize the current execution event in a way that explains the program's actual state and helps students understand why that state exists.

## Origin

VisUAL originated as part of [Lau-PyDE](https://github.com/laudotdev/Lau-PyDE_open-source), an open-source Python development environment. VisUAL now serves its own learning-focused purpose: making program execution and data structures easier to inspect, question, and understand through accurate, step-by-step visualization.
